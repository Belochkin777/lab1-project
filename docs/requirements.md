# Лабораторная работа 4. Анализ рисков и управление требованиями

## Область проекта

Рассматривается учебный консольный трекер задач из лабораторных 1–3: Python 3.12, локальное хранение в `tasks.json`, команды для работы с задачами, один студент в роли владельца продукта, разработчика и тестировщика. Сервер, база данных и сторонние API не входят в текущую версию. Требования описывают ближайший MVP и последующее расширение по инкрементной модели.

## Протоколы условных интервью

Интервью смоделированы для учебного задания и не являются реально проведёнными беседами. Дата фиксации сценариев: 26.11.2026. Цитаты ниже — условные формулировки, созданные для проверки требований; перед использованием в реальном проекте их нужно заменить ответами фактических пользователей.

### Интервью И-1 — студент

- Дата и время: 26.11.2026, 14:00 (условный сценарий).
- Роль: студент, пользователь консольных инструментов.
- Контекст: записывает учебные дела между занятиями на одном компьютере.
- Вопросы: Как вы фиксируете задачи сейчас? Что теряется или отнимает время? Какие сведения нужны при добавлении? Как находите задачу позже? Нужны ли сроки? Что должно происходить при ошибке файла?
- Условные цитаты: «Хочу быстро добавить дело одной командой»; «После перезапуска список не должен пропасть»; «Если задача уже сделана, хочу видеть это сразу».
- Выводы: быстрое добавление и просмотр — основные сценарии; локальное сохранение обязательно; нужен ясный статус выполнения.

### Интервью И-2 — преподаватель

- Дата и время: 26.11.2026, 14:30 (условный сценарий).
- Роль: преподаватель, оценивает демонстрацию учебного проекта.
- Контекст: проверяет, что приложение можно запустить и показать без настройки сервера.
- Вопросы: Что важно увидеть на демонстрации? Как понять, что задача сохранена? Какие ошибки следует объяснять? Как проверять команды? Какие ограничения должны быть в инструкции? Что означает пустой список?
- Условные цитаты: «Команды должны быть понятны без отдельного интерфейса»; «Нужен предсказуемый пример запуска»; «Ошибочное действие должно объяснять, как исправиться».
- Выводы: нужна справка и понятные сообщения; демонстрационный сценарий должен быть воспроизводимым; основные команды должны иметь проверяемые результаты.

### Интервью И-3 — начинающий разработчик

- Дата и время: 26.11.2026, 15:00 (условный сценарий).
- Роль: начинающий разработчик, потенциальный сопровождающий.
- Контекст: запускает проект из клона репозитория и читает исходный код.
- Вопросы: Что мешает первому запуску? Какие поля задачи полезны? Как вы исправляете опечатки? Как удаляете устаревшие записи? Что ожидаете при повреждённом JSON? Нужны ли внешние библиотеки?
- Условные цитаты: «Хорошо, если можно обойтись стандартной библиотекой»; «Опечатку удобнее исправить, чем удалять и вводить заново»; «Повреждённый файл нельзя молча перезаписывать».
- Выводы: важны простая установка и стандартная библиотека; редактирование и удаление полезны после базового MVP; ошибки хранения нужно обрабатывать без потери данных.

## Область релиза

В первом MVP обязательны добавление, просмотр, сохранение, отметка выполнения, справка и базовые ограничения данных. Редактирование, удаление одной задачи, фильтр и оптимизации UX планируются как следующие инкременты. Массовое удаление исключено из релиза, чтобы снизить риск случайной потери данных. Нефункциональные требования проверяются на локальной среде и не подразумевают серверную нагрузку.
